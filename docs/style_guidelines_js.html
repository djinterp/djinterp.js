JavaScript Coding Style Guide

The counterpart of djinterp's style_guide_c.md and style_guide_cpp.md, for the port. Written 2026-11-17.

This is the style of djinterp.js, in the order and form of djinterp's C and C++ guides. Where the language has the same thing to say, the section has the same name and the same rule. Where JavaScript has no such thing (include guards, macros, the preprocessor), the section says what stands in its place. Where this guide is silent, the C guide governs, and after it the C++ guide's additions, as far as JavaScript allows.

Each rule is one of three kinds:

  • ruled the owner has ruled on it; the ruling is named.
  • checked a tool in tools/ holds every file to it.
  • Unmarked: recommended, the house style written for the port on 2026-11-14 and not yet ruled on point by point.
This guide and JS_STYLE.md. docs/JS_STYLE.md is djinterp.js's file of style, changed only through the owner (JS3). This guide carries every rule in it, and adds the C guide's rules that the port follows without the file saying so. Which of the two governs from now on is open (D28, section 17). Until it is ruled, JS_STYLE.md governs wherever the two differ.

1. Layout

The port is one tree. A module's path is the reference's own path for the same thing, under src/, with djinterp's inc/djinterp/ and its language folder dropped: inc/djinterp/c/option/option_env.h becomes src/option/option_env.js, and inc/djinterp/tools/cli/c/cli_settings.h becomes src/tools/cli/cli_settings.js. A JavaScript module is both a header and its source, so one file stands for the pair.

PathHolds
src/djinterp.jsthe interface a page calls: open, run, on and the rest. It has no counterpart in the reference
src/MODULE/FILE.jsthe port of a reference module, at the reference's path
src/text/what the reference does inside another file and the port keeps apart: reals written and read, and text cut at a limit
tests/MODULE/FILE.test.jsa module's tests, mirroring src/
tests/transcripts/what the reference wrote, recorded by a tool, never by hand (section 14)
tools/the checks, and the C programs that record transcripts and write the generated data, built against the reference unchanged
generated/what the tools write: JSON, and a module for each file that a page imports. Committed; never edited by hand
types/the declarations the type check writes from the JSDoc. Committed; never edited by hand
examples/pages that use the port
docs/documentation

The port knows only itself.owner's word, 2026-11-16 Nothing in the repository (sources, tests, tools, examples, documents) names or needs a library other than djinterp.js. The reference, djinterp, is the one thing the port speaks of, since it is what the port follows.

2. General formatting

2.1 Spacing

Line length

As the C guide: a line is measured in characters, the count of Unicode code points on it, without its line break.

  • No tab characters anywhere. check_style.js
  • UTF-8, with no byte-order mark.
  • Single-width characters only. A wide character or an emoji is written by its code point in a string, as '\u{1F600}', never as a literal.
  • 80 characters at most.check_style.js In the port this is a limit, not the C guide's target: every line of every file people write is held to it. A long string is broken into parts joined with +. A row of a Markdown table, which cannot be broken, may pass it.
  • Depth is not a reason to run long. A line that is long because it sits five levels deep wants a function taken out of it.

Generated files, recorded transcripts and types/ are not held to this section. The generator is; its output need not be.

Whitespace

  • Four spaces to a level. Spaces, never tabs.
  • No space at the end of a line.check_style.js
  • LF line breaks; no carriage return. check_style.js
  • Every file ends with exactly one line break. check_style.js
  • Line related things up where it helps the eye: the = of a run of declarations, the names and descriptions of @param tags, the operators of a boolean expression.

2.2 Module guards

None. An ES module is evaluated once for each address it is imported by, so the C guide's include guard has no work to do. A module never guards against being loaded twice, and never sets a global to say that it has been.

2.3 Constant names

There are no macros. What the C guide says of a macro's name, that no two may share it with different meanings, holds for the port's exports: a name is exported by one module only, and a module that needs another's imports it.

2.4 Imports

Import what you use. Every module imports exactly what its own code needs, and does not lean on another module to bring it.

  • A path is relative (./ or ../) and ends in .js. Under src/ there is no bare name: nothing is imported from a package.
  • Generated data comes first, as a default import: import data from '../../generated/option.js';
  • Then the port's modules. A few names are imported by name (import { cutAt } from '../text/cut.js';); a module whose functions are used throughout is imported whole, under its file's name in camelCase (import * as optionEnv from './option_env.js';).
  • In tests/ and tools/, node's own modules come first, written with node: (import assert from 'node:assert/strict';), then an empty line, then the port's.
  • An import that runs past 80 characters breaks after its closing brace, with from on the next line, indented four.

The C guide's trailing comment on each include is not used: an import names what it brings, so the comment would say it twice.

import data from '../../generated/option.js';
import { formatReal } from '../text/real_format.js';
import { readReal } from '../text/real_read.js';
import { STATUS, fail, ok } from './option_common.js';

2.5 Brackets

  • Every opening brace of a function or a block is on its own line, in the column of the line that opened it: a function, an if, a loop, a switch, an arrow function's block.
  • No if, else or loop without braces, even for one statement.
  • An object or array literal opens its brace on the line it starts on.
if (_text.length <= _limit)
{
    return _text;
}

2.6 Boolean expressions

As the C guide. An expression of more than one condition is held in one pair of parentheses, each condition in its own, one to a line, their opening parentheses lined up and their operators aligned. A single condition takes no extra pair.

// a high surrogate kept and its low one cut off
return _text.slice(0, ( (last >= 0xD800) &&
                        (last <= 0xDBFF) &&
                        (next >= 0xDC00) &&
                        (next <= 0xDFFF) ) ? (_limit - 1) : _limit);

The same holds for a while, a return and an assignment: while ( (_line[at] === ' ') || and so on. A conditional expression's test is parenthesized when it is more than a name: ((power < 10) ? '0' : '').

2.7 Function calls and returns

As the C guide: a call with more than one argument, or one that runs past 80 characters, puts each argument on its own line, aligned with the first after the opening parenthesis.

return putInner(_registry,
                (typeof _statement === 'string')
                    ? envInner.cstr(_statement)
                    : null,
                _source);

The port keeps one exception the C guide does not name: a call whose arguments are all short (a name, a literal, index + 1) stays on one line when it fits, as formatG(_value, 17) and _text.slice(0, nul) do.

2.8 Variable declarations and initialization

  • Validate parameters first, then declare.
  • Declare each variable where it is first used, and give it its value in the same statement.
  • const for anything never assigned again; let otherwise. Never var.
  • Line up the names and = of a run of declarations.
const whole    = digits.slice(0, exponent + 1);
const fraction = digits.slice(exponent + 1).replace(/0+$/, '');

2.9 Control flow and spacing

  • Most ifs and loops have a comment above them saying what they are for.
  • An if is followed by an empty line, unless the next line closes an outer block.
  • A return is preceded by an empty line, unless it is the first statement of its block.
  • A function that gives nothing ends in an explicit return; (5.3).

3. Naming conventions

3.1 Names

D17a, 2026-11-16 Identifiers are the reference's names, in camelCase. The module is the namespace, so the C prefix goes, and each _ and the letter after it become that letter in capitals: d_option_env_assign_from is optionEnv.assignFrom. A name is found in the C by putting the underscores back.

WhatFormExample
a function or variablecamelCase assignFrom, statusName
a type (a @typedef)PascalCase, the same words D17a OptionEnv, EventEntry
a named constantcapitals and underscores, as the reference'sSTATUS.KEY_ABSENT, DEPTH_MAX
a parametera single leading underscore _text, _limit
a private field#m_ and the name #m_count
a module imported wholeits file's name in camelCase optionEnvRegistry
a word the language keepsa trailing underscore, exported under the wordimport_, exported as import
a filethe reference's own name option_env.js
datathe reference's spelling, exactly sidebar_width, name_count, bind.value
the interface a page callsshort words where it can open, run, on

A named constant, as in the C guide, is a const standing in for a literal or holding a fixed table: MAX_PATH_LENGTH, STATUS. The rule is about that role, not the keyword: a const holding a value worked out at run time is an ordinary variable and stays camelCase.

const MAX_PATH_LENGTH = 4096;                 // named constant

function isValid(
    _path                                     // a parameter
)
{
    const length = _path.length;              // const, not a constant

    return length < MAX_PATH_LENGTH;
}

3.2 Reserved identifiers

  • No leading underscore except a parameter's.
  • No double underscore anywhere. The language keeps that form for its own (__proto__), as C keeps it.
  • No name strict code refuses or the language may take: arguments, eval, let, static, implements, package and the rest. Use the trailing underscore of 3.1.
  • Never assign to, or create, a global.

4. Comments

4.1 Comment style

  • // comments by default.
  • Block comments for: the file's banner; its table of contents; and a function's or a type's comment (/** ... */, or the C guide's /* ... */ in a module not yet held to the strict mode, as 5.2 says).
  • Section and entry markers are the // forms of 4.3.
  • An ordinary comment begins in lower case unless its first word is a name or keeps its capitals.
  • Prose says what is true, plainly. No "we".

4.2 File header comments

Every file people write begins with the reference's banner, in the comment of its language, 80 characters wide, with the reference's fields at the reference's columns.

/*******************************************************************************
* djinterp.js [option]                                          option_common.js
*
*   What every part of the option machine answers with: a result that is a
* value or a status, and the statuses with the reference's own codes, names
* and messages. An expected failure is a value here, as it is in the
* reference; nothing in the machine throws one.
*   reference: inc/djinterp/c/option/option_common.h, at 3eb096c9
*
*
* path:      /src/option/option_common.js
* link(s):   TBA
* author(s): Samuel 'teer' Neal-Blim                         created: 2026.11.15
*                                                            revised: 2026.11.16
*******************************************************************************/

Rules:

  • The geometry is the C guide's: the rules end on character 80, the file's name ends on 80, the created: value ends on 80 with revised: beneath it, and the values of path:, link(s): and author(s): begin on 14.
  • All five fields, always. link(s): is TBA until there is one. Dates are YYYY.MM.DD.
  • The title is djinterp.js and a tag in brackets. The tag is the folder the file sits in: [text], [option], [event], [interp], [cli]; [tests] for a test and [tools] for a tool. src/djinterp.js, at the top of src/, has none. (The C guide's tag is the top folder; the port's tree is shallow enough to name the nearest.)
  • The description is prose. Each paragraph's first line is indented two more spaces than the rest.
  • A port of a reference module names it, with the commit the port follows: reference: PATH, at COMMIT. tools/regenerate.sh writes the commit when the reference moves.
  • path: is the file's own. check_style.js
  • An HTML file carries the same banner in an HTML comment, two spaces in; a shell script, in # lines.

4.3 Structure, numbering and contents

A module with more than one section has a table of contents after its banner, and numbered dividers in its body that match it, in the C guide's decimal form.check_style.js

The port's modules number two levels: sections (1.) and entries (1.1). An entry's marker carries no text, as the C guide's item markers carry none; the entry's own comment begins on the next line. A module that one day needs a third level uses the C guide's subsection divider at the second (// 1.1 Name and a line of hyphens) and its item markers at the third (// 1.1.1).

The table of contents:

/*
TABLE OF CONTENTS
=================
1.  STATUSES
    --------
    1.  STATUS
    2.  STATUS_MECHANICAL_FLOOR
    3.  statusName
2.  RESULTS
    -------
    1.  ok
    2.  fail
*/
  • A section's name is in capitals, two spaces after its number, with a line of hyphens beneath it exactly as long.
  • An entry is indented four, numbered from 1 under each section, two spaces after its number (one after a two-digit number). An entry may name several things that share one marker: 1. KIND, SOURCE, SOURCES, GLOBAL, NONE, DEPTH_MAX.
  • No empty line inside the table.
  • The table is the body's: each section's name and number are its divider's, and it lists as many entries as the section has markers.check_style.js

The body:

import data from '../../generated/option.js';


//==============================================================================
// 1.  STATUSES
//==============================================================================

// 1.1
/**
 * The statuses, by the reference's names without their prefix.
 *
 * @type {Readonly<Record<string, number>>}
 */
export const STATUS = ...
  • Two empty lines before each section's divider, and two empty lines nowhere else.check_style.js
  • A section's description, when it has a useful one, follows its closing rule at once, as the C guide's does. Then one empty line, and the first entry.
  • One empty line between entries.
  • A function the module does not export has no marker and no line in the table: it stands in its section, before the entries that use it, and its comment names it (5.2).

4.4 Comment formatting

  • Indent only the first line of each paragraph; the lines after it align with the comment's text.
  • A JSDoc comment is a description, an empty * line, then its tags: @param for each parameter, with its type in braces, then @returns. The names and descriptions of the @params line up.
  • JSDoc stands where the C guide writes Doxygen. It is a format read by the type check and by editors; no generator is run. D17b, 2026-11-16
/**
 * The first units of a text, as many as a limit allows, and one fewer
 * where the last of them would be the first half of a surrogate pair.
 *
 * @param {string} _text   the text.
 * @param {number} _limit  the most units to keep; under 1 keeps none.
 * @returns {string} the text, whole or cut.
 */

4.5 Brief comment format

For a small declaration that is not a function (a constant or a table inside a module), the C guide's brief form:

// MAX_PATH_LENGTH
//   constant: the longest path a settings file may have.

An exported constant or type carries JSDoc instead, with @type or @typedef, since that is what an editor and the type check read.

5. Functions

A JavaScript function is declared and defined in one place, so the C guide's two comments, the contract on the declaration and the mechanism on the definition, become one: the contract above the function, in JSDoc, and the mechanism as // comments inside it where it applies, or as prose after the tags, as the C guide does for a file-local function.

5.1 Exported functions

  • Every exported function has a JSDoc contract: what it does, its @params and what it @returns.
  • Parameters one to a line, indented four; the closing parenthesis on its own line; then the opening brace on its own line. A function with no parameters keeps () on its name's line.
  • A default value follows its parameter: _options = {}.
  • Exports are declared where they stand (export function, export const). An export list (export { ... }) is only for a name exported under another (export { import_ as import };) or for modules the interface hands on whole.
// 2.2
/**
 * A real as the option machine writes one: "%.17g", which is enough
 * digits for any double to read back as itself.
 *
 * @param {number}  _value  the double.
 * @returns {string} the text.
 */
export function formatReal(
    _value
)
{
    return formatG(_value, 17);
}

5.2 Functions inside a module

D25, 2026-11-17 A function a module does not export has a JSDoc comment in the C guide's form: /**, then the function's name on its own line, then what it does with its first line indented, then @param and @returns.

/**
 * bitLength
 *   The bits of a positive whole number.
 *
 * @param {bigint} _value  the number.
 * @returns {number}
 */
function bitLength(
    _value
)
{
    ...
}
  • In a module held to the strict mode (tools/strict_modules.js ), every function inside it has this comment. check_style.js
  • A module not yet held to it keeps the C guide's plain form until it is (D24): /*, the name, what it does, */. It moves to the JSDoc form when it joins the strict mode.
/*
cstr
  A string as C reads one handed to it without a length: up to its
first NUL.
*/

5.3 Functions that give nothing

As the C guide's void functions:

  1. No @returns.
  2. An explicit empty return; at the end. Every such function in src/ has one (14, measured 2026-11-17).

5.4 Arrow functions

  • For a callback or a short value, not for a function with a name.
  • Parameters in parentheses, always, and named as parameters: (_payload) =>.
  • A block body opens its brace on its own line, in the column of the line the arrow is on.
  • An expression body stays on the arrow's line when it fits.
event.stepMake((_payload) =>
{
    // a handler that gives nothing lets the event
    // pass on
    ...
})

5.5 Test functions

  • A test is node's test(name, function). Its name is a sentence saying what holds: 'a cut that would part a pair is one unit earlier'.
  • Its body is an arrow function, with its brace on its own line.
  • One test file for each module, at the module's path under tests/.
  • Assertions are node:assert/strict's.
  • A test has no length limit.
test('a cut is at the limit, for text that has no pairs', () =>
{
    assert.equal(cutAt('abcdef', 4), 'abcd');
});

6. Failures and errors

The C++ guide's rule, which the port shares: a failure a caller can handle is a value, not an exception.

  • Expected failures are values. Where the reference returns a status, the port returns the same status, by the same code and name, with the reference's message: a row out of range is refused as djinterp refuses it.
  • Throw only for a misuse no correct caller makes, such as a value of the wrong type handed in by the programmer: a TypeError for a wrong type, an Error for the rest. The message begins with the function's name and a colon: 'run: neither a line nor an array of words'.
  • A function that gives a promise breaks the promise for a misuse; it does not throw past it.
  • Never throw for control flow.
  • @throws is written for a misuse, and only there. A failure that is a value is described under @returns.

7. Language and checks

  • ES modules, in .js files, with "type": "module" in package.json. A module's code is strict by the language's rule.
  • No build step. What is in the repository is what a page imports.
  • No dependency at run time. Not one package. Tests and tools use what node ships with.
  • The same code in a browser and in node. Nothing under src/ reads a node built-in (fs, process, Buffer).
  • Node 22 for the tests: node --test.
  • No globals. A module exports what it offers and touches nothing it did not import.
  • === and !==, never == or !=.
  • ?? and ?. are the language's and are used. A bigint holds what needs 64 bits (section 13).

The checks stand where the C guide's warning flags stand:

The type check is a tool beside the style check, never a step a page needs, and the repository does not depend on it: its path is given on the command line. The strict mode comes in a module at a time; a module joins tools/strict_modules.js when it has no finding there. D24, 2026-11-16

A finding genuinely not worth putting right is suppressed at the narrowest scope, with a comment saying why, never for the project. There are none today.

8. Assertions

  • What the C guide asks of a static assertion (a stated assumption about a type that the code depends on), the port asks of its JSDoc: a type written down is a type the check holds the code to.
  • Nothing under src/ asserts at run time: node's assert is node's, and a page has none. A check of a caller's input is validation, and a failure is a value (section 6).
  • Tests assert with node:assert/strict.

9. Conditional code

The port has no preprocessor, and in its place the rule is shorter still: nothing under src/ asks where it is running. There is no test of window, document, process or globalThis (none, measured 2026-11-17). What differs between a page and node is handed in by the caller: a page that keeps its settings hands its Storage to storageFile, and anything else keeps them with memoryFile, which holds them in memory.

10. Control transfer

JavaScript has no goto; the C guide's rule for it holds for break, continue and labels. They are used where they remove nesting or a repeated line, never where they add either.

  • for (;;) for a loop whose end is inside it.
  • A label only to leave several loops at once, named for what happens there. There are none today.
  • Every case of a switch that has statements ends in break, return or continue; no case falls into the next.

11. Function size and complexity

As the C guide: a function does one thing, nameable without "and". The numbers are the tripwire.

MeasureLimitEscalation
Length100 lines, without the comment above it; none for a testtake a function out
Nesting4 levels of braces inside the body return early, or take a function out

Passing a limit wants a reason, as a dispatch table or a parser's switch may have. Five functions pass 100 lines today (section 16).

12. Types

  • A type is a @typedef in JSDoc, named in PascalCase, with a @property for each field, their names and descriptions lined up.
  • A record's fields keep the reference's spelling (3.1).
  • An exported constant carries its @type.
  • {*} says a value's type is not yet written down. A module held to the strict mode has none where a type can be named.
  • types/ is what the type check writes from these, and is never edited.

13. What the reference fixes

The C guides have no such section; the port needs one, since the reference is its oracle and JavaScript's own habits differ from C's in ways that change bytes.

  1. Integers. A number is exact to 253 − 1. A value is a number when its range lies inside ±(253 − 1), and a bigint when it does not; a row with no stated range is a bigint if the reference holds it in 64 bits. 64-bit arithmetic is never done in numbers.
  2. Reals as text. Never String(v), toFixed or toPrecision. The reference writes %.17g; the port has one function that writes as it does, formatReal in src/text/real_format.js, tested against the C library's own output, exact ties among them: a value halfway between two texts is written with the even digit, as C writes it, and never as JavaScript's rounding would.
  3. Reals from text. Never Number() or parseFloat: Number("") is 0, and parseFloat("1abc") is 1. Read to the grammar the reference accepts, with readReal in src/text/real_read.js, and refuse the rest as it does.
  4. Not a number. Any NaN is written nan. D4, 2026-11-16
  5. Text. Text is a JavaScript string, counted in UTF-16 units. D3, 2026-11-16 A cut at a limit never parts a surrogate pair: where it would, it is one unit earlier (cutAt).D23, 2026-11-16
  6. Order. Where the reference's output has an order, the port makes that order on purpose. A Map's order of insertion is not a reason.
  7. Nothing a result depends on reads the clock or Math.random.
Valuedjinterp (%.17g) JavaScript String(v)

14. Transcripts and generated data

The reference is the oracle. The port passes when it gives the reference's bytes.

  • A transcript is three files in tests/transcripts/: NAME.in, what was given to the reference; NAME.out, what it wrote, byte for byte; and NAME.meta, the program, its arguments, the reference's commit and the date. A tool records it; no one writes one by hand.
  • When the reference moves, every transcript is recorded again at the new commit (tools/regenerate.sh), and a difference is a change to review, not to accept.
  • Whatever the reference holds as data (rows and their ranges, statuses and their messages, the kit's texts) is written out as JSON by a tool and read by the port. It is never typed again in JavaScript. Each generated file's first field names the reference's commit.

15. File structure

A module

  1. The banner (4.2).
  2. An empty line, and the table of contents, for a module with sections.
  3. An empty line, and the imports (2.4).
  4. Two empty lines, and the first section's divider.
  5. Each section's entries, each a marker and the entity's comment, then the entity.
/*******************************************************************************
* djinterp.js [foo]                                                       bar.js
*
*   Brief description of the module.
*   Extended description: what it ports, and anything a reader should know
* first.
*   reference: inc/djinterp/c/foo/bar.h and src/djinterp/c/foo/bar.c, at
* COMMIT
*
*
* path:      /src/foo/bar.js
* link(s):   TBA
* author(s): Author Name                                     created: YYYY.MM.DD
*                                                            revised: YYYY.MM.DD
*******************************************************************************/

/*
TABLE OF CONTENTS
=================
1.  OPERATIONS
    ----------
    1.  someFunction
*/

import data from '../../generated/foo.js';
import { cutAt } from '../text/cut.js';


//==============================================================================
// 1.  OPERATIONS
//==============================================================================
// Declares the operations the module offers.

/**
 * someHelper
 *   What the helper does, in a sentence or two.
 *
 * @param {string} _name  what it is given.
 * @returns {boolean}
 */
function someHelper(
    _name
)
{
    ...
}

// 1.1
/**
 * What the function does, for a caller.
