A wasm configuration: djinterp’s own module behind the port’s interface

Decide by 2026-11-30, the wasm module’s last windowAffects open’s options, a new src/wasm/, the transcripts, the page

You wrote on 11-18, at 14:49, with the wasm module’s beta build: djinterp.js has opt-in features, and a wasm configuration would be one of them. It was in the cards. START drew the interface with await so that what answers it could change, to a wasm module in a Worker or to a remote engine, and the first version was to have neither. That much your word rules: the configuration is optional, and the port stays the default. What is open is its form.

The beta (seven steps on 6fe35d43, for windows from 11-23 to 11-30) gives a console over five host imports declared in host.h: a configuration text in and a status out, a line in and a reply out. The program does not answer through it yet: the console asks for a program’s handler, which is not built, and log.c does not build until a module has a mutex (a no-op, since a module has one thread). Until it does, none of this can be checked, so nothing is built before the ruling and the handler. What the port would ask of a reply (the status, the two streams apart, whether standard error is a terminal, and the names a set kept) is written up in docs/FOR_THE_LANES.md, for you to relay.
