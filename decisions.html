64-bit INT rows in JavaScript (J11)

Decide before uxoxo.js reads a valueAffects every page that reads or writes an integer setting

An INT row holds an int64_t with an int64_t range. A JavaScript number is exact only to 253 − 1. Inside, the port holds every integer as a BigInt, so no comparison, range check or flag operation is ever inexact. The question is the type a page is handed.

Measured on the fixture: of its 20 INT rows, 11 declare no range, so each can hold any int64_t. START's "most rows are small" is true of values, but not of what rows are declared to hold.

Decision 2
Option
Advantages
Disadvantages
Recommendation: C. It's the only option under which nothing is refused and nothing is silently wrong. The rule a page needs is one line: declare a range and the row is a number. A value is taken in as a number, a bigint or a decimal string; a number that isn't an exact integer is a TypeError, and one outside 64 bits a RangeError.

Text inside the port: bytes or JavaScript strings

Decide before uxoxo.js reads a valueAffects every offset, width and limit the port reports

The reference measures text in bytes. A script's refusal is reported at a byte offset. list and describe pad their columns by bytes. get cuts a value at 511 bytes. A frame's text arena fills by bytes. A JavaScript string is measured in UTF-16 units, and the two agree only for ASCII.

Room: how much a frame holds

Decide before rows come from the reference's own JSONAffects when a page meets CAPACITY and BUFFER_TOO_SMALL

A C frame is declared over fixed storage: so many bindings, variables and bytes of text. Past them it answers CAPACITY or BUFFER_TOO_SMALL, and its text arena compacts, which moves the generation. The port does all of this when a frame is given room, and the transcript session_room holds it to the reference.

The registry that open makes has the reference's configured room, read from generated data: 256 bindings, 64 variables, 4,096 bytes of text and 32 djins. A djin's own frame has no such default: in C, each is sized where it's declared.

Disadvantages

What a line is: a run of the program, or a turn in a session

Decide before uxoxo.js binds to the interfaceAffects what every line after the first answers

The reference's djinterp program is one process for one command line. It imports the environment, reads the settings file, takes the line's --set and --NAME options at the command line's standing, runs one command and exits. set binds at override's standing and writes the file, and the next process reads that value from the file.

The port's open is one start, and its lines share one registry. Measured, the two differ after the first line:

  • After set printer.style=json, the port's next get --show-origin printer.style says (override). The next native run says (file).
  • get --set printer.key_width=40 printer.key_width leaves key_width bound at the command line's standing for every later line. Natively the binding ends with the process.

The transcripts don't catch this. Their harness makes a fresh program for each line, as the reference is, so the page's own run is the one path they don't check.

Decision 7
Option
Advantages
Disadvantages
Recommendation: B. A port passes when its bytes agree with the reference's, and for these four commands the reference has one meaning of a line. A session is a reasonable thing for a console to want, but today it has no oracle. When the frozen command language defines one, the port takes it from there, with transcripts.

Splitting a line into words

Decide before uxoxo.js binds to the interfaceAffects every line a console or a panel sends; replaced by the frozen grammar after 12-11

The reference has no line splitter for these commands: a shell splits the line before the program starts. The command language that will define one freezes on 12-11, and it's in the port's second tier. A page's console has a line and needs words today.

The port's rule (djinterp.split): spaces and tabs separate words; "…" holds a word, with \" and \\ inside it; '…' holds one literally; spans that touch join; an unclosed quote is djinterp: error: a quote is not closed. tools/djinterp_fixture_main.c has the same rule in C behind --line, so the transcripts hold the two to each other. The rule is this session's invention, not the reference's.

Decision 8
Option

Disadvantages
Recommendation: D. The words form is the reference's own interface, so it should be on the page's interface too, and it's the form that programs should use. The line form is for people, and it's the part to treat as provisional until 12-11.

The parser and the kit: how the program reads its command line

Decide before a console is shown to anyoneAffects every command line that isn't one of four plain commands

The reference reads a command line with djinterp's argument parser (58,507 lines in 42 C sources) and its command-line kit (12,721 lines in 8). Neither is ported. The port's djinterp_commands.js reads the four commands' arguments with a model of what the parser does for them, written from the parser's source and checked against the reference.

What the model covers, and how it was checked: a missing command, a word that's no command, arguments a command doesn't expect, an operand it requires, --show-origin, the settings options --set and --NAME, and the parser's "did you mean". 60,000 fuzzed command lines agree with the reference, near misses of every name among them.

What it doesn't cover: help, completion, --help, --version, -q, -v, --color, a bare --, and short options run together. The port answers each as a word it doesn't know, where the reference runs it. The fuzzer never produces them, so the agreement above says nothing about them.

What this morning showed. "Did you mean" was on the not-ported list, and 7,050 fuzzed lines had agreed without it. Then a fresh seed happened on a near miss of list and differed. With the fuzzer made to produce near misses, two more differences followed (how an argument like ---color is classed, and a space dropped from the end of the arguments listed), and a hand-typed line found a fourth: which word the kit names. All four are now ported, from arg_suggest.c, arg_parse.c and cli_program.c. A model is exact as far as its fuzzer reaches and no further.

Decision 11
Option
Advantages
Disadvantages
Recommendation: D. The accurate port of four commands isn't 71,228 lines, but it isn't today's model either: a console that refuses help isn't djinterp's. B closes that, and the rule from this morning goes with it: nothing joins the model without the fuzzer being taught to produce it first.

Three are for the lanes that own the program, the kit and the option machine, for you to relay. The rest are done or are the port's to do.

  • djinterp get -- NAME refuses NAME. Measured on the reference's own binary at d20c0b23: djinterp get -- plugin_path answers get: the following argument was not expected: plugin_path, while djinterp get plugin_path prints it. set -- NAME=VALUE and describe -- DJIN take their operands after --. It looks unintended. The port doesn't model -- yet (decision 11), so it hasn't copied it.
  • The kit names half a word. With several arguments and no command, the word it calls "not a command" is cut at the first space of the joined arguments: djinterp 'two words' --x answers 'two' is not a command. With one argument it names the whole of it. The port does the same, and the transcript program_commands holds both.
  • d_option_env_statement_end reads past a script's end when it's given an offset beyond the terminator. The port's fuzzer keeps within the script. Lane E can say whether that's the caller's contract or wants a guard.
